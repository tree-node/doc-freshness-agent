設計ドキュメント

正本（source of truth）の変化を検知し、依存する社内文書の陳腐化・違反の疑いを根拠付きで特定するエージェント。本書はコンセプト、機能要件、絞り込みパイプライン、デモ・データ方針までの全決定事項を統合したもの。

§1コンセプト

社内の課題（設計書の陳腐化、規定の法令違反、営業資料の記載遅れ）はすべて同一構造——「正が変わった → 依存する文書が腐った」——を持つ。本プロダクトはドキュメントチェッカーではなく、正本と派生文書の依存関係を保持し、正本の変化を派生側へ伝播させるエンジンとして設計する。参照ソースはユーザーが自由に登録でき、業界を問わず適用できる（デモは労働法令シナリオに絞る）。

設計原則1 — 主語はイベント。一覧の主語はドキュメントではなく「正本の変更イベント」。1つの改正の配下に影響文書がぶら下がる。緊急度は鮮度（最終更新日）ではなく、施行日までの残日数・影響件数・確信度から算出する。

設計原則2 — 書き込み権限を持たない。修正は「該当箇所のみ書き換えた文書を生成しダウンロード提供 → 人間が置換」。プロダクトは顧客文書への書き込み権限を一切要求しない。PR自動作成は本思想と矛盾するため実装しない。

設計原則3 — 影響なしも見せる。「精査20件中、要対応3件・影響なし17件」を明示する。何を見て何を見なかったかを隠さないことが信頼の源泉であり、定期監視されている安心感につながる。

§4取り込みとチャンク分割

登録とファイル検出

監視対象はフォルダ単位で登録し、配下を再帰的に取り込む。巡回時にファイルリストの差分を取り、後から追加されたファイルを検出して取り込む。ファイル名・フォルダ構造は判定に使わない（中身で判定する）。

文書種別の自動付与

取り込み時に安価モデルで文書種別（規定／契約書／設計書等）を推定して付与する（1文書1回）。ファイル名と中身の不一致が前提のため、手動登録にはしない。種別は絞り込みではなく優先度付けに使う——種別不明・低確信度のチャンクは除外せず通す（見逃し側に倒す原則）。

チャンク分割

  • 固定長ではなく文書構造に沿った分割。法令・規定類は条・項単位、md/設計書は見出し（H2/H3）単位、docxは見出しスタイル単位
  • サイズ目安 200〜800トークン。長い条は項で再分割、短い条は無理に結合しない
  • 表は「直前の見出しに属する1チャンク」として明示的に拾う（別表は改正の影響を受けやすく、分割から漏れやすい）
  • 前文・附則など条マッチに掛からない残りテキストも捨てずにチャンク化する
  • 法令側はe-Gov法令APIで条構造付きXMLを取得できるため、正規表現ではなくXML構造をそのまま分割に使う（仕様は実装前に確認）

チャンクメタデータ

  • 文書ID + 構造パス（「就業規則 > 第3章 > 第12条」）— UI表示・根拠提示に直結
  • 文字オフセット（開始・終了）— マーキング表示と修正案の置換位置特定に必要
  • 文書種別（自動推定・確信度付き）— Stage 1の優先度付けに使用
  • 本文ハッシュ — キャッシュキー（§7）の材料

埋め込み対象テキストには構造パスを先頭に付与する（「就業規則 第3章 勤務 第12条 …」）。表示用本文と埋め込み用テキストを分けて持つ。

§5候補絞り込みパイプライン

目的はコスト削減と判定精度の向上を同時に満たすこと。長いコンテキストは判定精度を下げるため、この2つは同じ方向を向く。件数は例。

Stage 0 — 差分の抽出とクエリ化

中位モデル1イベント1回

生の差分テキストは検索クエリとして質が悪い（「『努めなければならない』を『しなければならない』に改める」を直接検索しても社内規定に当たらない）。モデルを1回呼び、構造化された「変更の意味」に変換する。出力スキーマ：変更の要旨／影響しうる業務領域／検索キーワード群／施行日。以降の全段階の精度がこの出力に依存する。

Stage 1 — ハイブリッド検索

LLM不使用

事前にインデックス化したチャンクに対し、ベクトル検索＋キーワード検索（BM25等）を併走させスコアを統合する。法令・規定は「第12条」「特定個人情報」等の固有表現の完全一致が効くため、ベクトル単独では取りこぼす。正本↔監視対象の紐付け情報を事前フィルタに使う。

Stage 2 — 再ランク

安価モデル

検索は「似ているか」を測るが、必要なのは「影響を受けるか」。同じ法律を引用しているだけの無関係チャンクは検索スコアが高く出る。安価モデル（または専用リランカー）で採点し直す。判定ではなくトリアージ——精度より速度と安さを優先してよい。

Stage 3 — 精査

高性能モデル

唯一コストをかける段階。入力：変更後の条文全文／候補チャンク＋前後文脈／文書メタデータ。出力：影響の有無／根拠／該当箇所の位置／修正案／確信度。低確信度時はより強いモデルへエスカレーション。

プロンプトに手順を明示する：まず文書の性質と法令の適用可能性を判断し、その後に影響を判定する。判定理由カテゴリに「適用外」を持たせる（例：業務委託・準委任契約に労基法は適用されない。労働時間の記載が濃くても正解は影響なし。テキスト類似度では確実に誤検出する最高難度ケースであり、正しく除外できればデモのハイライトになる）。

§6見逃し（偽陰性）への担保

コンプライアンス用途では見逃し1件で製品の信頼が消える。絞り込みは「保証の代替」ではなく「保証の上に乗せる最適化」。過検出（偽陽性）は棄却フローで吸収できるため許容し、見逃しゼロを優先する。

4つの担保 — 要件として必須
  1. ① 紐付け済み文書は無条件で精査に通すユーザーが明示的に登録した対応は検索スコアに関係なく必ずStage 3へ。人間の宣言を機械のスコアで上書きしない。
  2. ② 件数固定ではなくスコア閾値を併用する「上位10件」だけだと11件目の本命を落とす。閾値以上は全通し＋上限件数ガードの二段構え。
  3. ③ 絞り込みの過程を可視化する「3,000チャンク中、精査50件・対象外2,950件」を画面表示。何を見なかったかを隠さない。
  4. ④ 定期全件精査をバックストップに持つ日常はイベント駆動で安く、月1回など低頻度で全監視対象を精査する網羅モードを併設。

§7キャッシュと起票の分離

判定結果は次のキーでキャッシュする：

cache_key = hash( 正本差分 ) × hash( 対象チャンク ) × prompt_version
  • 巡回して差分がなければコストは完全にゼロ。巡回頻度を上げてもコストは増えない
  • prompt_versionを含めないと、プロンプト改善後も古い判定が残り続ける
  • 同一内容のチャンクは同一キーになるため、設計上、同一内容に異なる判定は出せない（重複ファイルの片方だけ指摘するハルシネーションを構造的に防止）
判定と起票は別レイヤーに分ける。判定はチャンクハッシュ単位でキャッシュするが、アラートは該当チャンクを含む全ファイルインスタンスに展開して起票する。1対1にすると、同一内容の2ファイルが1件のアラートに畳まれ「片方しか表示しない」事故になる。監査ログはファイル単位で残す必要があるため、この分離は監査要件とも整合する。

これとは別レイヤーで、ゲートウェイ側のプロンプトキャッシュも効く（§9）。精査で10候補に繰り返し渡す条文全文の共通部分が乗り、二段キャッシュ構成になる。

§9OrcaRouterの役割分担

位置づけ：コスト削減の主役は多段絞り込みの設計。OrcaRouterはそれを計測・証明・保護するインフラ。プレゼンでもこの順で語る。

ルーティングDSLorcarouter/auto は限定使用

各段階の難易度は設計時点で確定している。autoに任せると精査が安価モデルに回され見逃しリスクになるため、DSL（YAML + CEL）で「精査→高性能モデル固定、それ以外→最安」とルールを書き、リポジトリでバージョン管理する（「ルーティング方針をコードレビューできる」という本番運用の訴求）。autoの使用はStage 0程度に留める。無料プランでのDSL利用可否は実装前に確認。不可ならAPI呼び出し時のモデル直接指定で代替。

リクエストログrequest logs / zero markup

全呼び出しにモデル・レイテンシ・コストが記録され、上乗せ$0の透明な明細。コスト実測表示機能の実装コストがほぼゼロになる。

プロンプトキャッシュcached tokens

キャッシュ済みトークンはプロバイダーのキャッシュ料金で課金。精査時に繰り返す条文全文が乗る。§7の自前キャッシュと二段構成。

ガードレールPII Shield — 最後の防波堤

PII検出時は課金前にブロック（400）する仕組みで、マスキングして通す仕組みではない。送信前マスキングはアプリ側で実装し、ゲートウェイは多層防御の最終層と位置づける。この構成をセキュリティのスライドにする。

自動フェイルオーバーmid-stream failover

429/5xxを応答開始前に別モデルへ再試行。「本番で通用する」の体現であり、当日ライブデモの事故保険。

予算・キー管理budget caps

スコープ付きキーの予算設定で「1イベントあたりのコスト上限ガード」を自前実装せずに済む可能性。無料プラン（Hacker）での利用範囲は要確認。

§10デモ・データ方針

正本 — 実在の法令を使う

正本は作らない。法務省・国税庁等の公開データ（e-Gov）を直接参照する。「法律は嘘をつけない」——審査員が根拠リンクを踏むと本物の条文に飛ぶことが、捏造ダミーでは出せない説得力になる。

デモ中の「改正」は時間の巻き戻しで起こす

直近に実際にあった労基法関連の改正を1つ選び、スナップショットを改正前の条文で初期化しておく。デモで巡回を実行すると、本物のe-Govとの差分として実在の改正を本当に検知する。検知・判定・根拠のすべてが本物のデータで動く。プレゼンでは「直近の改正を再現している」と正直に言う。どの改正を使うかの選定が、監視対象データ作成の前提となる最優先タスク（監視対象は改正前ルール準拠で書く必要があるため）。

領域の優先度と深さの傾斜

領域深さ役割
労働系（労基法）全部盛り本命。正常系・紛れ文書・重複・雑然フォルダ・正解セットをここに集中。雇用形態バリエーション（雇用契約・業務委託・準委任）を含む
個人情報系最小構成違反2件＋正常2件程度。目的は精度比較ではなく「正本を差し替えるだけで別領域に効く」汎用性の実演
金融・商取引系作らないスライドで拡張先として言及するのみ

本番デモに載せるのは、労働系 vs 個人情報系で精度が出たほう。

監視対象の作り込みポイント

  • 違反文書だけでなく法令通りの正しい文書も用意（「影響なし」の正検知を見せる）
  • 同一内容ファイルを複数配置し、片方だけ指摘する挙動が出ないことを検証（§7の設計で構造的に保証される——「テストで確認」ではなく「設計上出せない」と言える）
  • 直接的な文書だけでなくそれらしい記述が紛れた文書（給与規程内の深夜手当の一文等）を混ぜる。文脈で拾えるかが本質＝「AIである必然性」の証明
  • フォルダ構造を複数パターン（整理済み／雑然）。ファイル名と中身の不一致も含める——「メモ_final_v2.docxの中身が雇用契約書でも本文で判定するので拾える」は本番デモの1シーンに昇格させる
  • 業務委託・準委任契約は労基法適用外のため正解は「影響なし（適用外）」。§5 Stage 3の適用可能性判断とセットで最高難度のテストケース

正解セットと精度の見せ方

  • 正解表は「ファイル名＋該当条・該当記述＋期待判定（影響あり／なし／適用外）」の3点セット、箇所粒度で作る（製品の主張と同じ粒度でないと数字がズレる）。種別推定の正解も1列追加
  • 見せ方は率単体ではなく内訳：「影響あり10件中10件を検出、影響なし15件中14件を正しく除外（1件は過検出）」。母数が小さいため率単体は避け、率を言うなら分母とセット
  • 見逃しと過検出を分けて報告：「見逃しゼロを優先し、過検出は棄却フローで吸収する設計」と§6と一貫したストーリーで語る
  • 本番前に数値を実測し、悪ければ閾値調整してから臨む
