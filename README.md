# ドキュメント鮮度監視エージェント

**正本（source of truth）の変化を検知し、依存する社内文書の陳腐化・違反の疑いを根拠付きで特定するエージェント。**

法令が改正された瞬間、全国の就業規則・雇用契約書・社内規定は一斉に「古く」なります。しかし、どの文書のどの箇所が影響を受けたかを人力で追い切ることはできません。本プロダクトは、法令などの「正本」の変化を検知し、影響を受ける文書と箇所を自動で特定、根拠と修正案を添えて人間に提案します。

## 何ができるか

- **正本の変更検知**: 政府（デジタル庁）が運営する公式法令データベース「e-Gov 法令検索」の法令データと保存済みスナップショットを突き合わせ、条文の差分を検知。デモ用の擬似データではなく、本番・デモともに本物の法令を参照します
  - 実行は手動（画面の「今すぐチェック」または CLI）です。**定期巡回は設計済み・未実装**
  - 正本を GitHub リポジトリの実装コードに差し替えれば設計書の陳腐化検知になります（**設計のみ。未実装**。DESIGN.md の二経路表を参照）
- **影響箇所の特定**: 改正の意味を解析し、監視対象フォルダ内の文書から影響を受ける箇所を特定。**ファイル名ではなく本文で判定**するため、`メモ_final_v2.docx` の中身が雇用契約書でも見つけます
- **根拠付きの指摘**: 「就業規則 第7条が、改正後の労基則第5条に抵触」という形で、条文の原文リンクとセットで提示
- **修正の提案**: 該当文のみを書き換えた修正版ファイルを生成。**適用は必ず人間の承認を経ます**（システムは文書への書き込み権限を持ちません）
- **影響なしの明示**: 「20件を確認し、3件が要対応・17件は問題なし」——確認しなかったものが何件あって、なぜかまで表示します
- **監査ログ**: 誰が・いつ・どの改正を根拠に・どう判断したかを、根拠法令とセットで記録

## デモについて

デモでは、実在の法令改正を使用しています。システムのスナップショットを改正前の条文で初期化し、本物の e-Gov との差分として**実在の改正を実際に検知**させています（検知・判定・根拠提示のすべてが本物の法令データで動作します）。

監視対象の社内文書（就業規則・雇用契約書等）は、デモ用に作成した**架空の会社の架空の文書**です。実在の企業・人物とは一切関係ありません。

## アーキテクチャ

```
正本の変化                絞り込みパイプライン                人間の承認
─────────                ──────────────────                ─────────
法令 (e-Gov) ──┐    差分を変更単位に分解 (Stage 0)
               ├──▶  ハイブリッド検索 3,000→50 (Stage 1)  ──▶ 起票 ──▶ UI ──▶ 承認 ──▶ 修正版DL / PR
実装 (GitHub) ─┘    再ランク 50→10 (Stage 2)
  ※未実装             高性能モデルで精査 10→3 (Stage 3)
```

図の 3,000 と各段の件数は設計上の想定規模です。**デモ環境の実測は正本2法令・12 文書・171 チャンク**。

### 設計原則

1. **主語はイベント** — 文書の「鮮度」ではなく「正本の変更」を起点に、影響を伝播させる
2. **本体を直接書き換えない** — システムは提案物（修正版ファイル / PR）のみを生成し、適用は人間が行う
3. **影響なしも見せる** — 何を確認し、何を確認しなかったかを隠さない
4. **見逃し側に倒す** — 迷ったら候補に残す。失敗は黙って握りつぶさず「要人間確認」として起票する

### コストと精度の設計

全文書を毎回 LLM に渡す素朴な実装と比べ、多段絞り込みにより **1 イベントあたりのコストを 1/12 〜 1/24** に削減しています（イベントごとの実測値を画面に表示）。絞り込みは同時に判定精度も向上させます——長大なコンテキストは判定を不安定にするため、コスト削減と精度向上が同じ方向を向く設計です。

精度は正解表 15 件（影響あり 10・影響なし 4・適用外 1、箇所粒度）で **見逃し 0・過検出 2**。過検出 2 件はいずれも確信度 0.55 で要人間確認フラグ付きです。母数が小さいため、率ではなく内訳で示しています。

見逃し（偽陰性）への担保として、①ユーザーが紐付けた文書の無条件精査、②スコア閾値と件数上限の併用、③絞り込み過程の可視化、④低頻度の全件精査モード、の4つを設計し、**①〜③を実装しています**（④は未実装）。

### セキュリティ

- 文書本文は**判定に必要なチャンクのみ**を送信します（文書全体は送りません）
- 外部から取得したテキスト（条文・文書本文）はタグで区切り、**指示として解釈しない**プロンプトインジェクション対策を実装（`app/llm/client.py` の `INJECTION_GUARD` / `wrap_untrusted`、テストは `tests/test_pipeline.py`、指示文を仕込んだ検証用文書を `demo-data/` に同梱）
- LLM ゲートウェイ（OrcaRouter）のガードレールを最終防波堤とする多層防御
- システムは監視対象への書き込み権限を一切要求しません

**現時点で実装していないもの**（ハッカソンのスコープ外として意図的に外しています）:

- **送信前の PII マスキング** — 設計済み・未実装です。現状、氏名等を含む文書本文はそのまま LLM ゲートウェイに送信されます。実運用では必須の項目です
- **認証・権限管理（SSO 含む）** — 単一利用者のローカル実行を前提としています
- プロンプトインジェクションの突破試験 — 上記の対策は入れていますが、既知の突破手法に対する検証は行っていません

## セットアップ

```bash
# 1. クローン
git clone <this-repo>
cd <this-repo>

# 2. 環境変数（.env はコミットされません）
cp .env.example .env
# .env に OrcaRouter の API キー等を設定

# 3. バックエンド（Python 3.11 以上）
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload

# 4. デモを動かせる状態を作る（正本の取得＋監視対象の取り込み。1〜2分）
python scripts/setup_demo.py

# 5. フロントエンド（別ターミナル）
cd frontend
npm install
npm run dev
```

`data/` 配下（スナップショット・索引・検知結果）はリポジトリに含めていません。
**各自の環境で作れることを確かめられるように**、生成物は配らず手順を配る方針です。

**セットアップの最後に案内される 2 つの `run` コマンドを先に実行してください。**
画面の「今すぐチェック」でも同じことができますが、変更が多い法令（労働基準法は 41 件）を
すべて確認すると 1 時間近くかかります（押す前に所要時間と費用の見積りが表示されます）。
`run` コマンドは条を 1 つに絞るので 2〜3 分で終わります。

起動後、`http://localhost:5173` を開いてください。設定画面から正本（法令）の追加と監視のオン／オフができます。
監視対象フォルダは `.env` の `WATCH_ROOT` で指定します（既定は `./demo-data/監視対象`）。
